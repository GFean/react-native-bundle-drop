# 0.11.0 — Native Fingerprinting Beta

This release candidate adds automatic native compatibility while keeping manual
runtime versions as the default. It also improves upload metadata, Expo setup,
manual rollback control and update reporting.

## Native fingerprinting

Opt in through `bundle.drop.config.js`:

```js
runtimeVersion: {
  compatibilitySource: 'fingerprint',
},
```

Build and distribute a new native app after enabling it. Ordinary uploads then
calculate compatibility automatically. Compatible JavaScript changes can reach
that binary; detected native changes require another native build. Collection
failures stop the operation without falling back to a manual runtime.

For hybrid control, add optional `ios` and `android` runtime strings beside the
selector. Both the explicit boundary and the fingerprint must match. Update
policies remain independent of compatibility selection.

Fingerprinting is Beta and opt-in. Scheme 1 has a frozen calculation contract;
future SDK upgrades do not silently select a different scheme. See the
[configuration guide and coverage limits](../native-fingerprint.md).

## Uploads and compatibility metadata

- Uploads record manual or fingerprint compatibility explicitly. The full native
  identity continues to govern delivery and patch compatibility.
- Optional build metadata records Android `versionCode` or iOS `CFBundleVersion`,
  allowing binary versions such as `1.0.0 (122132)` in a compatible dashboard.
- Bare iOS build-number detection recognizes standard Xcode build settings with
  ordinary unquoted project paths. Ambiguous or computed values stay unknown;
  custom build systems can pass `--build-number` explicitly.

The upload feedback, dashboard links and release-notes options introduced in
0.10.0 remain available.

## Runtime and delivery fixes

- Ordinary manual rollback requests stage an intent until explicit apply, which
  refreshes authority and validates the fallback. Confirmed-revocation and native
  crash/incompatibility safety recovery retain their existing protection. See
  [manual rollback behavior](../manual-rollback.md).
- Unmanaged patch-artifact HTTP 401/403 responses can try the trusted resolve
  decision's supplied full ZIP once for the same target. Verification and managed
  authorization rules remain intact. See [fallback details](../unmanaged-patch-auth-fallback.md).
- Installed-report deduplication survives recovery to the embedded app, with
  bounded history scoped to the install/project identity. See
  [reporting behavior](../install-report-deduplication.md).
- Expo setup diagnostics report update-ownership conflicts clearly. Transient
  Kotlin sessions no longer destabilize Expo fingerprints, and implicit Debug
  suppression no longer persists OTA-disabled state into a Release launch.
- iOS automatic health acknowledgement binds rendered content to the native
  module's own React runtime and startup attempt, including bridgeless runtimes.
  Manual health acknowledgement and crash-recovery thresholds remain unchanged.

## Upgrading

This candidate uses native revision `0.6.3`. Update the dependency, run `pod install`
for iOS, and rebuild the native app to include its native changes. An OTA cannot
replace native code or enable fingerprinting in an older binary.

Existing fingerprint Beta apps also need rebuilding against this release's
revised scheme 1 baseline. Patched minimatch and glob change some ignore-pattern
matches; use the same SDK version and dependency lock for native builds and OTA
uploads. Earlier Beta calculators are not interchangeable with this release.

Keep matching native dependencies, configuration and declared build context when
building the app and uploading updates. Autolinked package changes can alter the
fingerprint even when a particular change only affects tooling or JavaScript.
Same-fingerprint releases remain eligible for patches under the existing rules.
